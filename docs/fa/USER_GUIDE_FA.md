# راهنمای کاربری CodeBench

این سند نحوه کار با رابط کاربری CodeBench را توضیح می‌دهد: شرح کامل ۱۰ نما و
چرخه کامل کار، از ساخت آزمایش تا گزارش‌گیری و تحلیل هوش مصنوعی.

رابط کاربری یک SPA تک‌صفحه‌ای است که در مسیر `/` سرو می‌شود و مسیریابی بین
نماها با hash انجام می‌شود. سه رنگ زبان در کل برنامه ثابت است: C++ کهربایی
(amber)، Java رز (rose) و Python زمردی (emerald).

## نمای کلی نماها

| نما | کاربرد |
|---|---|
| Workbench | ساخت و ویرایش آزمایش: انتخاب واریانت، زبان، دیتاست، سایز و سیاست اندازه‌گیری |
| Catalog | کاتالوگ راستی‌آزمایی‌شده ۲۰ واریانت با جزئیات و شروع سریع یک draft |
| Runner | اجرای زنده: پیشرفت واقعی job ها، console زنده، لغو اجرا |
| Results | مرور نتایج: فیلتر، مرتب‌سازی، توزیع مشاهدات، خروجی خام هارنس |
| Compare | مقایسه بین‌زبانی: نمودار مقیاس‌بندی log-log و نوارهای نسبی با whisker |
| Regression | مقایسه دو run: baseline در برابر candidate با حکم رگرسیون |
| History | تاریخچه اجراها، جزئیات هر run، خروجی گزارش، اجرای مجدد و clone |
| Environment | مشخصات host و در دسترس بودن هر سه موتور |
| AI Insights | تحلیل اختیاری یک run تمام‌شده توسط مدل زبانی |
| Settings | پیش‌فرض‌های آزمایش، ارائه‌دهنده هوش مصنوعی و آستانه رگرسیون |

## چرخه کامل کار

### ۱) ساخت آزمایش (Workbench)

در نمای Workbench یک draft آزمایش می‌سازید:

- **نام و توضیح:** نام الزامی است (حداکثر ۱۲۰ کاراکتر).
- **واریانت‌ها:** از میان ۲۰ واریانت ۶ خانواده انتخاب کنید. فیلتر بر اساس
  خانواده و جستجو در دسترس است. اگر واریانتی در زبان‌های انتخابی در دسترس نباشد،
  هشدار داده می‌شود.
- **زبان‌ها:** هر ترکیبی از C++ و Java و Python. در دسترس بودن هر زبان (از
  endpoint `/languages`) کنار انتخاب‌ها نمایش داده می‌شود.
- **دیتاست:** نوع دیتاست باید توسط همه خانواده‌های انتخابی پشتیبانی شود؛
  مثلاً دیتاست‌های مرتب‌سازی برای خانواده گراف معنا ندارند و اعتبارسنجی جلوی
  چنین ترکیبی را می‌گیرد.
- **اندازه‌های ورودی:** چند سایز می‌توانید انتخاب کنید (presetهای آماده از ۲۵۶
  تا ۱,۰۰۰,۰۰۰؛ محدوده مجاز ۸ تا ۲,۰۰۰,۰۰۰). هر واریانت سقف خودش را دارد —
  مثلاً `insertion_sort` بیشتر از ۴۰۹۶ قبول نمی‌کند.
- **سیاست اندازه‌گیری:**
  - `warmup` (پیش‌فرض ۲): تعداد تکرار گرم‌سازی پیش از اندازه‌گیری.
  - `repetitions` (پیش‌فرض ۵، حداقل ۲): تعداد تکرار اندازه‌گیری‌شده. هر تکرار
    یک observation خام ذخیره می‌شود.
  - `seed` (پیش‌فرض ۲۰۲۶۱۰۱۶): seed تولید ورودی. seed یکسان + دیتاست و سایز
    یکسان = ورودی bit-identical بین هر سه زبان.
  - `timeoutMs` (پیش‌فرض ۱۸۰,۰۰۰): سقف زمان هر job؛ پس از آن کل process group
    با SIGKILL متوقف و job با وضعیت TIMEOUT ثبت می‌شود.
  - `continueOnError` (پیش‌فرض روشن): شکست یک job اجرای بقیه را متوقف نمی‌کند.

اعتبارسنجی سمت کلاینت آینه همان قواعد سرور است؛ تا رفع خطاها دکمه اجرا فعال
نمی‌شود. با **Save** آزمایش ذخیره و با **Run** ذخیره + اجرا می‌شود. آزمایش‌های
ذخیره‌شده قبلی هم از همین نما قابل بازیابی و ویرایش‌اند.

### ۲) مرور کاتالوگ (Catalog)

نمای Catalog کاتالوگ کامل واریانت‌ها را با دسته‌بندی خانواده نشان می‌دهد: کلید،
دسته (`hand-written` یا `standard-library`)، پیچیدگی، دیتاست‌های مجاز، اندازه‌های
پیش‌فرض، سقف سایز، «عملیات اندازه‌گیری‌شده» و قرارداد خروجی. از این نما می‌توانید
یک واریانت را مستقیم به draft آزمایش اضافه کنید. شرح کامل کاتالوگ در
[ALGORITHMS_FA.md](ALGORITHMS_FA.md).

تفاوت دو دسته را جدی بگیرید: واریانت‌های `hand-written` ساختار الگوریتمی یکسانی
در هر سه زبان دارند و نسبت‌هایشان به مقایسه «زبان + runtime» نزدیک است؛
واریانت‌های `standard-library` روال کتابخانه استاندارد هر زبان را صدا می‌زنند و
تفاوتشان بهاندازه مهندسی کتابخانه، به runtime مربوط است.

### ۳) اجرا و مشاهده پیشرفت واقعی (Runner)

پس از زدن Run، به نمای Runner منتقل می‌شوید. اجرا به‌صورت سری انجام می‌شود
(در هر لحظه حداکثر یک run فعال) و پیشرفت از وضعیت واقعی job ها به‌روز می‌شود:

```
QUEUED → PREPARING → RUNNING → VERIFYING → ANALYZING → COMPLETED | FAILED | CANCELLED
```

- **PREPARING:** کامپایل موتور C++ (با کش mtime) و کلاس‌های Java — تا خطای
  toolchain پیش از هر اندازه‌گیری ظاهر شود.
- **RUNNING:** اجرای ترتیبی job ها (ضرب واریانت × زبان × سایز). شمارنده
  `completedJobs/totalJobs` و job جاری (`currentJob`) پس از هر job به‌روز می‌شود.
- **VERIFYING:** مقایسه checksum ها با reference و بین زبان‌ها.
- **ANALYZING:** بررسی پایداری نتایج (هشدار برای CV ≥ ۱۰٪) و ثبت نتیجه نهایی.

console زنده، خطوط ثبت‌شده `RunLog` را با سطح‌بندی (info / success / warn / error)
نشان می‌دهد. دکمه **Cancel** اجرای فعال را لغو می‌کند: job جاری با kill کل گروه
پروسهایش متوقف و run با وضعیت CANCELLED ثبت می‌شود. این پیشرفت واقعی است، نه
شبیه‌سازی‌شده؛ هر job یک پروسه واقعی هارنس است.

### ۴) بررسی نتایج و مشاهدات خام (Results)

نمای Results نتایج یک run یا کل آزمایش را فهرست می‌کند:

- فیلتر بر اساس زبان و واریانت، و مرتب‌سازی بر اساس میانه، میانگین، CV، سایز
  یا زمان.
- هر سطر شامل آمار کلیدی (میانه، میانگین، CV، فاصله اطمینان)، وضعیت راستی‌آزمایی
  و نشانگر **×lang** است. این نشانگر یعنی `crossLangMatch` برقرار است: checksum
  ورودی و خروجی این سطر با همتاهایش در سایر زبان‌های همان گروه یکسان بوده و مقایسه
  مستقیم مجاز است. نبودنش در یک run چندزبانه یعنی آن گروه بررسی را شکست داده.
- بازکردن هر سطر، توزیع مشاهدات خام را به‌صورت نوار توزیع نشان می‌دهد: هر
  observation یک نقطه روی محور لگاریتمی، box از Q1 تا Q3 و خط میانه. داده پرت
  (outlier) همین‌جا دیده می‌شود.
- خروجی خام هارنس (`rawOutput`) — همان JSON که Google Benchmark / JMH / pyperf
  چاپ کرده‌اند — از طریق endpoint `runs/{id}/raw` قابل بازرسی و دانلود است؛ هیچ
  عددی از تجمیع خود هارنس «به ارث» نرسیده است.

راهنمای تفسیر هر آماره در [RESULTS_AND_STATISTICS_FA.md](RESULTS_AND_STATISTICS_FA.md).

### ۵) مقایسه بین‌زبانی (Compare)

نمای Compare یک run تمام‌شده را انتخاب می‌کند و برای هر واریانت:

- **نمودار مقیاس‌بندی (log-log):** زمان اجرا (محور y) بر حسب اندازه ورودی (محور
  x)، هر دو لگاریتمی؛ یک خط برای هر زبان. روی محور log-log الگوریتم O(n) خطی با
  شیب ۱ است و O(n²) شیب ۲؛ مقایسه شیب‌ها رفتار پیچیدگی را بصری نشان می‌دهد.
- **نوارهای مقایسه:** میانه هر (واریانت، زبان) به‌صورت نوار افقی با whisker خطای
  (فاصله اطمینان یا پراکندگی) در انتهای نوار. همپوشانی زیاد whisker دو نوار یعنی
  رتبه‌بندی آن دو به‌اثبات نرسیده است.

مقایسه را فقط بین سطرهای دارای نشانگر ×lang و با درنظرگرفتن CV انجام دهید.

### ۶) مقایسه رگرسیون (Regression)

نمای Regression دو run را به‌عنوان baseline و candidate انتخاب می‌کند و برای هر
جفت (واریانت، زبان، سایز) همخوان حکم صادر می‌کند:

- **REGRESSION / IMPROVEMENT:** فقط وقتی تغییر میانه هم از آستانه عملی
  (پیش‌فرض ±۱۰٪، قابل تنظیم از Settings) و هم از نویز ترکیبی
  (`sqrt(cv_baseline² + cv_candidate²)`) بزرگ‌تر باشد.
- **INCONCLUSIVE:** تغییر از آستانه یا از نویز کوچک‌تر است — تفاوتی که از نویز
  قابل تشخیص نیست، رگرسیون گزارش نمی‌شود.
- **NOT-COMPARABLE:** راستی‌آزمایی یکی از دو طرف شکست خورده است.
- **NO-DATA:** آن ترکیب در یکی از دو run وجود ندارد.

گزارش مقایسه، قابلیت مقایسه را هم صریح می‌گوید: `workload-differs` اگر
واریانت‌ها/زبان‌ها/دیتاست/سایزها/seed دو run فرق داشته باشند و `environment-differs`
اگر مدل CPU یا تعداد هسته‌ها متفاوت باشد. برای یک مقایسه معنی‌دار، دو run از یک
آزمایش (یا دو آزمایش با config یکسان) اجرا کنید.

### ۷) تاریخچه و گزارش‌گیری (History)

نمای History فهرست run ها را (جدیدترین اول، همراه sparkline و شمارنده job ها)
نشان می‌دهد. برای هر run:

- بازکردن جزئیات: وضعیت، پیشرفت، config، محیط ثبت‌شده و نتایج.
- **خروجی گزارش:** تولید و دانلود گزارش JSON / CSV / Markdown. گزارش، تعریف
  آزمایش، آمار هر نتیجه، مشاهدات خام، وضعیت راستی‌آزمایی، محیط و محدودیت‌ها را
  در بر می‌گیرد (خروجی هوش مصنوعی به‌عمد داخل گزارش قطعی نمی‌آید).
- **اجرای مجدد** همان آزمایش (برای ساخت جفت baseline/candidate) و **clone**
  آزمایش (کپی تعریف با همان config).

### ۸) محیط اجرا (Environment)

مشخصات host (سیستم‌عامل، معماری، مدل CPU، تعداد هسته، حافظه کل، runtime میزبان)،
سیاست ایزولاسیون و در دسترس بودن هر سه موتور را به‌صورت زنده نمایش می‌دهد. قبل
از استناد به یک عدد بیرون از این سیستم، این نما را ببینید: نتایج CodeBench
مختص همان محیط ثبت‌شده است، نه رتبه‌بندی جهانی زبان‌ها.

### ۹) تحلیل هوش مصنوعی (AI Insights)

این نما برای یک run تمام‌شده (COMPLETED یا FAILED) تحلیل اختیاری می‌سازد:

1. ارائه‌دهنده و وضعیت آن را بالای نما ببینید (zai / ollama / disabled).
2. run موردنظر را انتخاب و **Analyze** را بزنید.
3. خروجی ساختاریافته در بخش‌های مشخص نمایش داده می‌شود: خلاصه، یافته‌های
   مشاهده‌شده، شواهد آماری، محدودیت‌ها، توضیحات محتمل (فرضیه)، آزمایش‌های
   پیشنهادی و سطح اطمینان مدل.

هر چیزی که مدل دریافت می‌کند فقط داده‌های ذخیره‌شده همان run است؛ خروجی با
schema اعتبارسنجی و از نظر grounding بررسی می‌شود و لایه هوش مصنوعی هیچ مسیر
کدی برای تغییر نتایج اندازه‌گیری ندارد. جزئیات در [AI_INSIGHTS_FA.md](AI_INSIGHTS_FA.md).

### ۱۰) تنظیمات (Settings)

- **پیش‌فرض‌های آزمایش:** مقدار warmup، repetitions، timeoutMs و seed که هنگام
  حذف این فیلدها از config یک آزمایش استفاده می‌شوند.
- **هوش مصنوعی:** انتخاب ارائه‌دهنده (`zai` / `ollama` / `disabled`)، آدرس
  Ollama (پیش‌فرض `http://localhost:11434`)، مدل و temperature.
- **آستانه رگرسیون:** درصد آستانه معناداری عملی (پیش‌فرض ۱۰).

## نکات کاربردی

- **سری اجرا می‌شود:** اگر run فعالی در جریان باشد، اجرای جدید با خطای 409 رد
  می‌شود؛ صبر کنید یا run فعال را لغو کنید.
- **seed را ثابت نگه دارید** تا بین اجراها فقط پیاده‌سازی/محیط تغییر کند، نه
  ورودی. برای مطالعه حساسیت به ورودی، seed را عوض کنید.
- **تکرار بیشتر، فاصله اطمینان تنگ‌تر:** عرض فاصله اطمینان تقریباً با 1/√n کوچک
  می‌شود؛ برای تفکیک تفاوت‌های زیر ~۵٪ به repetitions بالاتر نیاز است.
- **به CV نگاه کنید:** نتیجه با CV ≥ ۱۰٪ بهعنوان ناپایدار هشدار داده می‌شود؛
  آن را دوباره اجرا کنید (تکرار بیشتر، ورودی بزرگ‌تر یا ماشین آرام‌تر).
- **همه کارها با API هم ممکن است:** رابط کاربری فقط یک client از همان
  `/api/v1` است؛ نمونه curl در [API_FA.md](API_FA.md).
