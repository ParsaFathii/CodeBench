# تفسیر نتایج و آمار

هر نتیجه در CodeBench مجموعه‌ای از مشاهدات خام است — یک مقدار ns/op per هر تکرار
اندازه‌گیری‌شده — به‌همراه آمارِ محاسبه‌شده از همان مشاهدات. این سند معنای هر
آماره، زمان اعتماد به آن و نحوه خواندن نمودارها و نشانگرهای رابط کاربری را
توضیح می‌کند.

## آمارها، یکی‌یکی

همه مقادیر از `computeStats()` در `src/lib/bench/stats.ts` می‌آیند و از آرایه
ذخیره‌شده `observations` محاسبه می‌شوند.

| آماره | چیست | چه زمانی به آن اعتماد کنیم |
|---|---|---|
| `n` | تعداد مشاهدات خام | همه موارد زیر بهاندازه n خوب هستند. با ۵ تکرار پیش‌فرض، فاصله‌های پهن انتظار داشته باشید. |
| `min` / `max` | دو سر افراط مشاهدات | به‌تنهایی بهندرت معنادارند؛ `max` اغلب آرتیفکت scheduler یا GC است. |
| `mean` | میانگین حسابی | به outlier حساس است، اما مبنای فاصله اطمینان است. |
| `median` | صدک ۵۰ (درون‌یابی R-7) | **عدد اصلی گزارش.** در برابر outlier مقاوم است؛ برای نسبت‌های بین‌زبانی و اختلاف رگرسیون از همین استفاده کنید. |
| `stddev` | انحراف معیار نمونه‌ای (مخرج n − 1) | مقیاس پراکندگی run-to-run به ns. |
| `p5 / p25 / p75 / p95 / p99` | صدک‌ها (‏R-7، پیش‌فرض numpy/pandas) | شکل توزیع؛ `p95`/`p99` دنباله بالایی ناشی از تداخل (GC، ‏scheduler) را نشان می‌دهند. |
| `iqr` | p75 منهای p25 | پراکندگی میانه‌ها؛ مبنای قانون outlier. |
| `mad` | انحراف مطلق میانه‌ای نسبت به میانه | جایگزین مقاوم به outlier برای stddev. |
| `cv` | تقسیم stddev بر \|mean\| | پراکندگی نسبی؛ مبنای طبقه‌بندی پایداری. |
| `ci95` | فاصله اطمینان t با ۹۵٪ روی میانگین | در ادامه توضیح داده شده. |
| `outliersIqr` | مشاهدات خارج از [Q1 − 1.5·IQR, Q3 + 1.5·IQR] | علامت‌گذاری می‌شوند، **هرگز حذف نمی‌شوند**. |
| `stability` | پایدار / متوسط / ناپایدار | در ادامه توضیح داده شده. |

### ضریب تغییرات

`cv` به این پرسش پاسخ می‌دهد: «این اندازه‌گیری نسبت به اندازه خودش چقدر پرنویز
بود؟»

- **CV کمتر از ۳٪ — پایدار.** میانه یک برآورد محکم است؛ تفاوت‌های ۱۰٪ بین‌زبانی
  روی این ماشین تفاوت واقعی است.
- **۳٪ تا کمتر از ۱۰٪ — متوسط.** قابل استفاده، اما یک اختلاف ۱۰٪ بین دو نتیجه
  با CV متوسط ممکن است نویز باشد؛ به حکم مقایسه نگاه کنید.
- **CV برابر یا بیشتر از ۱۰٪ — ناپایدار.** coordinator وقتی run ای نتایج ناپایدار
  دارد هشدار ثبت می‌کند. عدد را یک نشانه تقریبی ببینید و اجرای مجدد (تکرار بیشتر،
  ورودی بزرگ‌تر، ماشین آرام‌تر) را بررسی کنید.

CV همان چیزی است که منطق رگرسیون بین run ها ترکیب می‌کند: یک مقایسه فقط وقتی
REGRESSION یا IMPROVEMENT اعلام می‌کند که تغییر میانه از هم آستانه عملی و هم
`sqrt(cv_baseline² + cv_candidate²)` بزرگ‌تر باشد.

### فاصله اطمینان در نمونه‌های کوچک

مقدار `ci95` یک فاصله اطمینان t دوسویه با ۹۵٪ روی میانگین است:
`mean ± t(df = n−1) · stddev / √n`. با ۵ تکرار پیش‌فرض، مقدار t برابر ۲.۷۷۶ است —
بیش از ۲.۵ برابرِ ۱.۹۶ نمونه بزرگ — پس فاصله، صادقانه درباره عدم قطعیت است.
پیامدهای عملی:

- هم‌پوشانی فاصله‌های دو نتیجه برابری را اثبات نمی‌کند، و عدم هم‌پوشانی‌شان شواهد
  خوبی از تفاوت واقعی است.
- فاصله روی *میانگین* محاسبه می‌شود که outlier ها را شامل می‌شود؛ میانه (جداگانه
  گزارش می‌شود) معمولاً برآورد نقطه‌ای مقاوم‌تری است.
- افزایش `repetitions` در config آزمایش، فاصله را تقریباً با آهنگ 1/√n تنگ می‌کند.

## خواندن نمودارها

رابط کاربری نمودارهای SVG خودش را می‌کشد (`src/components/bench/charts.tsx`)؛
هیچ کتابخانه نموداری در کار نیست.

**نمودارهای مقیاس‌بندی (log-log).** زمان اجرا (محور y) در برابر اندازه ورودی
(محور x)، هر دو با مقیاس لگاریتمی؛ یک خط per (واریانت، زبان). روی محورهای log-log
یک الگوریتم O(n) خطی با شیب ۱ است، ‏O(n log n) کمی تندتر و O(n²) شیب ۲. این
رفتار پیچیدگی را مستقیماً مرئی می‌کند: منحنی‌ای که سریع‌تر از شیب مورد انتظار
خانواده‌اش به بالا خم می‌شود معمولاً یعنی اثر cache یا فشار حافظه. *شیب‌ها و
موقعیت‌های نسبی* را مقایسه کنید نه فقط نقاط پایانی؛ مقادیر مطلق مختص همان محیط
هستند.

**نوارهای مقایسه.** نوارهای افقیِ میانه per (واریانت، زبان) به‌همراه whisker خطا
(فاصله اطمینان یا پراکندگی) حول انتهای نوار. whisker همان نشانه بصری «تفاوت بین
دو نوار ممکن است نویز باشد» است: اگر whisker دو نوار به‌شدت هم‌پوشان باشند،
رتبه‌بندی آن دو به اثبات نرسیده است. رنگ زبان‌ها در کل برنامه ثابت است: C++ کهربایی،
‏Java رز و Python زمردی.

**نوارهای توزیع.** per نتیجه: هر observation خام به‌صورت یک نقطه روی محور با
مقیاس لگاریتمی، یک box از Q1 تا Q3، یک خط میانه پررنگ و whisker تا min/max. اینجا
است که outlier ها مرئی می‌شوند — یک نقطه تنها دور از box، همان مشاهده‌ای است که
میانگین را از میانه دور کرد. box جمع‌و‌جور بدون نقطه سرگردان، شکل یک اندازه‌گیری
پایدار است.

**sparklineها.** خطوط روند کوچک (در بافت history و runner) روی مقادیر اخیر؛ برای
دیدن رانش بین run ها مفیدند، نه برای قرائت دقیق.

## نشانگرهای راستی‌آزمایی

هر نتیجه سه سیگنال راستی‌آزمایی دارد:

- `verificationStatus` — مقدار `PASSED`، ‏`FAILED` یا `SKIPPED` (وقتی خود job پیش
  از راستی‌آزمایی شکست خورده باشد).
- `refMatch` — آیا checksum کیس‌های ثابت موتور با reference پیاده‌سازی TypeScript
  هم‌خوان است؟ مقدار `false` یعنی پیاده‌سازی غلط است و زمان‌سنجی بی‌معنی است.
- `crossLangMatch` — آیا در گروه (variant, dataset, size)، همه زبان‌ها checksum
  ورودی *و* خروجی یکسان تولید کرده‌اند؟

نشانگر **×lang** که کنار یک نتیجه در نمای‌های Results و Compare نمایش داده می‌شود
یعنی `crossLangMatch` برقرار است: checksum ورودی/خروجی بین زبان‌ها هم‌خوان است، پس
این سطر با همتاهایش در زبان‌های دیگر مستقیماً قابل مقایسه است. نبود این نشانگر در
یک run چندزبانه یعنی آن گروه، برابری بین‌زبانی را شکست داده و مقایسه نامعتبر است.

شکست راستی‌آزمایی، نتیجه را `FAILED` می‌کند؛ مقایسه‌های درگیر چنین نتایجی به‌جای
عدد، سطر `NOT-COMPARABLE` برمی‌گردانند.

## متریک‌های حافظه / تخصیص

فقط موتور Java یک متریک تخصیص گزارش می‌کند: profiler مربوط به `gc` در JMH مقدار
`gc.alloc.rate.norm` (بایت تخصیص‌شده per عملیات) را می‌دهد که coordinator آن را در
`extraMetrics` زیر کلید `java.gc.alloc.rate.norm_b_per_op` ذخیره می‌کند. این متریک:

- به‌عنوان یک متریک ثانویه مختص Java و تأمین‌شده از JMH **برچسب‌گذاری** شده است؛
- **هرگز بین‌زبانی مقایسه نمی‌شود** — C++ و Python معادلی گزارش نمی‌کنند، پس
  هر مقایسه «تخصیص حافظه» بی‌معنی می‌شد؛
- درون خود Java مفید است: مثلاً توضیح می‌دهد چرا workload های hash با کلید `Long`
  با box شدن یا رشد `ArrayList<Integer>` نسبت به workload های آرایه اولیه در همان
  زبان، هزینه‌ای که می‌کنند را می‌دهند.

## تفسیر نسبت‌های بین‌زبانی

قواعد صحتی که از روش‌شناسی نتیجه می‌شوند:

- واریانت‌های دست‌نویس مقایسه زبانی تمیزتری هستند؛ واریانت‌های کتابخانه استاندارد
  بهاندازه runtime، کتابخانه‌ها را هم مقایسه می‌کنند.
- نسبت‌ها مختص همان workload و سایزند؛ شکاف ۳ برابری در n=10,000 به n=1,000,000
  تعمیم نمی‌یابد و شکاف‌ها اغلب با شکل ورودی جابه‌جا می‌شوند (پنج دیتاست مرتب‌سازی
  را ببینید).
- عملیات اندازه‌گیری‌شده به‌عمد هزینه‌های واقعی هر زبان را شامل می‌شود (کپی
  defensive، ساخت کانتینر، box شدن کلیدها در جاهای اصیل). پیش از نتیجه‌گیری، متن
  «عملیات اندازه‌گیری‌شده» را در [ALGORITHMS_FA.md](ALGORITHMS_FA.md) بخوانید.
- همه چیز مختص محیط است: پیش از نقل عدد به جای دیگر، snapshot محیط run را (‏CPU،
  هسته‌ها، بار سیستم) بررسی کنید.

## یک مثال کاربردی

یک سطر نتیجه از `GET /api/v1/experiments/{id}/results`:

```json
{
  "variantKey": "sorting.std_sort", "language": "python",
  "inputSize": 10000, "datasetType": "random_int",
  "verificationStatus": "PASSED", "refMatch": true, "crossLangMatch": true,
  "observations": [1785234, 1802111, 1760988, 1923450, 1776120],
  "stats": {
    "n": 5, "min": 1760988, "max": 1923450,
    "mean": 1809580.6, "median": 1785234,
    "stddev": 65403.5, "p5": 1762118, "p25": 1772330,
    "p75": 1843547, "p95": 1908217, "p99": 1920486,
    "iqr": 71217, "mad": 25123,
    "cv": 0.0361, "ci95": [1745069, 1874092],
    "outliersIqr": [], "stability": "moderate"
  }
}
```

نحوه خواندن:

- راستی‌آزمایی پاس شده و نشانگر ×lang برقرار است، پس این سطر مستقیماً با سطرهای
  `sorting.std_sort` زبان‌های دیگرِ همان run قابل مقایسه است.
- میانه ≈ ۱.۷۹ میلی‌ثانیه per مرتب‌سازی؛ میانگین توسط مشاهده ۱.۹۲ میلی‌ثانیه‌ای به
  بالا کشیده شده. outlier مربوط به IQR نداریم، اما `p95`/`max` یک دنباله را
  نشان می‌دهند.
- مقدار CV برابر ۳.۶٪ یعنی پایداری متوسط: قابل استفاده، اما مقایسه با یک نتیجه
  دیگر با CV متوسط باید به حکم رگرسیون (که CV ها را ترکیب می‌کند) تکیه کند، نه فقط
  نسبت خام.
- فاصله اطمینان روی میانگین حدود ‎±۳۳ میکروثانیه — تقریباً ‎±۱.۸٪ است. در برابر
  یک نتیجه همتای C++ مثلاً با میانه ۱۹۰ میکروثانیه، نسبت زبانی (~۹ برابر) از هر
  دو فاصله بزرگ‌تر است و *روی این ماشین و برای این workload* با اطمینان واقعی است.
- مشاهدات خام `observations` ذخیره شده‌اند، پس هر یک از این اعداد قابل بازمحاسبه
  است — هیچ‌چیز اینجا به تجمیع خود هارنس وابسته نیست.

## خطاهای رایج

- **مقایسه واریانت‌های کتابخانه استاندارد به‌عنوان تفاوت زبانی خالص.** واریانت
  `std_sort` یعنی `std::sort` در برابر quicksort دو محوری در برابر Timsort — سه
  الگوریتم متفاوت. فیلد `category` را بررسی کنید.
- **خواندن اختلاف‌های زیر آستانه به‌عنوان رگرسیون.** endpoint مقایسه دقیقاً برای
  همین است که آستانه و CV ترکیبی را در حکم لحاظ کند؛ به `INCONCLUSIVE` اعتماد
  کنید.
- **نقل عدد بدون محیط.** هر گزارش به همین دلیل snapshot محیط را در خود دارد؛ آن‌ها
  را با هم نگه دارید.
- **اعتماد به سطر راستی‌آزمایی‌نشده.** اگر `verificationStatus` برابر `PASSED`
  نباشد یا `refMatch` مقدار `false` باشد، آن زمان‌سنجی اندازه‌گیری الگوریتم
  موردنظر نیست.
