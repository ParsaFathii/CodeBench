# تحلیل هوش مصنوعی (AI Insights)

CodeBench یک لایه هوش مصنوعی اختیاری دارد که run های تمام‌شده را تفسیر می‌کند. این
لایه صرفاً یک مفسر فقط-خواندنی است: هرگز آمار محاسبه نمی‌کند، هرگز به رکوردهای
بنچمارک دست نمی‌زند و پلتفرم بدون آن هم به‌طور کامل کار می‌کند.

## انتزاع ارائه‌دهنده

فایل `src/lib/ai/provider.ts` یک interface کوچک (`status()` / `complete()`) را با سه
پیاده‌سازی تعریف می‌کند که در settings انتخاب می‌شوند
(`PUT /api/v1/settings` → فیلد `ai.provider`):

| ارائه‌دهنده | چیست | چه زمانی استفاده شود |
|---|---|---|
| `zai` | بک‌اند داخلی `z-ai-web-dev-sdk` که سمت سرور صدا زده می‌شود. پیش‌فرض این محیط. | کار بدون پیکربندی در جایی که SDK در دسترس است. |
| `ollama` | مدل‌های میزبانی‌شده محلی از طریق یک آدرس پایه Ollama (پیش‌فرض `http://localhost:11434`، قابل تنظیم). این adapter مدل‌های نصب‌شده را فهرست می‌کند و `/api/chat` را با `format: json` صدا می‌زند. | میزبانی خودتان با ملاحظات حریم خصوصی — شواهد روی همان ماشین می‌ماند. |
| `disabled` | بدون ارائه‌دهنده؛ تحلیل‌ها با خطای صریح شکست می‌خورند. | استقرار صرفاً بنچمارکی. |

تابع `GET /api/v1/ai/status` ارائه‌دهنده پیکربندی‌شده، در دسترس بودن زنده و مدلی را
که استفاده می‌کرد گزارش می‌کند. در دسترس نبودن ارائه‌دهنده هیچ‌گاه قابلیت‌های اصلی
بنچمارک را مسدود نمی‌کند.

## مدل دقیقاً چه داده‌ای دریافت می‌کند

payload شواهد در `buildEvidence()` (در `src/lib/ai/analyze.ts`) ساخته می‌شود و
**منحصراً از سطرهای ذخیره‌شده در دیتابیس برای همان run در حال تحلیل**:

- شناسه `runId`، وضعیت run، نام آزمایش و config آن؛
- خلاصه محیط (سیستم‌عامل، معماری، مدل CPU، تعداد هسته، سیاست ایزولاسیون) از
  snapshot محیط همان run؛
- per نتیجه تکمیل‌شده: کلید/نام واریانت، دسته، زبان، اندازه ورودی، دیتاست، وضعیت
  راستی‌آزمایی، ‏`refMatch`، ‏`crossLangMatch` و آمار محاسبه‌شده (‏n، میانه،
  میانگین، انحراف معیار، ‏cv، ‏p95، ‏min، ‏max، پایداری، تعداد outlier، متریک‌های
  اضافی مانند نرخ تخصیص Java)؛
- per job شکست‌خورده: کلید واریانت، زبان، اندازه ورودی و پیام خطا (کوتاه‌شده).

آنچه هرگز دریافت نمی‌کند: آرایه‌های observation خام (فقط آمار محاسبه‌شده از آنها)،
خروجی خام هارنس، اعتبارنامه دیتابیس یا داده هیچ run دیگری. چون payload فقط نتایج
ذخیره‌شده را در بر دارد، هیچ عددی نمی‌تواند وارد تحلیل شود که اندازه‌گیری نشده
باشد — از prompt نمی‌توان برای ساختن شواهد جعلی استفاده کرد.

system prompt علاوه بر این، مدل را به هشت قاعده مقید می‌کند؛ از جمله: هر ادعای
کمی باید از payload آمده باشد؛ فقط به واریانت‌ها/زبان‌ها/سایزهای حاضر در شواهد
ارجاع بده؛ «شواهد کافی نیست» یک پاسخ معتبر است؛ میان واقعیت‌های اندازه‌گیری‌شده،
آمار محاسبه‌شده، فرضیه‌ها و توصیه‌ها تمایز بگذار؛ نتایج را به‌صورت رتبه‌بندی جهانی
زبان‌ها ارائه نکن؛ پاسخ را به‌صورت یک شیء JSON منطبق با schema بده.

## schema خروجی ساختاریافته

پاسخ مدل parse و (با zod) در برابر این schema اعتبارسنجی می‌شود:

| فیلد | نوع / سقف | محتوا |
|---|---|---|
| `summary` | رشته، حداکثر ۲۰۰۰ کاراکتر | قرائت کلی run |
| `observed_findings` | حداکثر ۲۰ رشته، هر کدام حداکثر ۱۰۰۰ کاراکتر | واقعیت‌های مقید به واریانت / زبان / سایز مشخص |
| `supporting_run_ids` | حداکثر ۱۰ رشته با حداکثر ۶۴ کاراکتر | باید دقیقاً شناسه همان run در حال تحلیل باشد |
| `statistical_evidence` | حداکثر ۲۰ رشته | اعداد نقل‌شده از payload (‏CV، میانه‌ها، اختلاف‌ها) |
| `limitations` | حداکثر ۲۰ رشته | محدودیت‌ها: مختص محیط بودن، n کوچک، نتایج ناپایدار |
| `possible_explanations` | حداکثر ۲۰ رشته | صریحاً فرضیه، نه اندازه‌گیری |
| `recommended_experiments` | حداکثر ۲۰ رشته | اجراهای بعدی که ارزش انجام دارند |
| `confidence` | `high` \| `medium` \| `low` | اطمینانِ خود-ارزیابی‌شده مدل |

هر چیزی که parse نشود (پس از حذف fence های اختیاری markdown و استخراج بیرونی‌ترین
شیء JSON) یا اعتبارسنجی نشود، رد می‌شود؛ سطر تحلیل با وضعیت `FAILED` به‌همراه خطا
ذخیره می‌شود.

## اعتبارسنجی grounding

پس از اعتبارسنجی schema، تابع `checkGrounding()` تحلیل را در برابر شواهد بررسی
می‌کند:

- **شناسه‌های run:** هر عضو `supporting_run_ids` باید برابر شناسه run در حال تحلیل
  باشد. ارجاع به run های خارجی رد می‌شود.
- **ارجاع‌های واریانت:** توکن‌های snake_case که در خلاصه، یافته‌ها، شواهد آماری یا
  توضیحات ظاهر می‌شوند با کلیدهای واریانت حاضر در run تطبیق داده می‌شوند. توکنی
  که شبیه یکی از شناسه‌های واریانت ما باشد (بررسی‌شده در برابر فهرست شناسه‌های
  شناخته‌شده و پیشوندهای شناسه واریانت) اما جزئی از run نباشد، نشانه آن است که
  تحلیل به چیزی که اندازه‌گیری نشده ارجاع داده است.

تحلیل رد‌شده با وضعیت `FAILED` و خطایی به شکل `analysis rejected (ungrounded): …`
ذخیره می‌شود و API کد `502` برمی‌گرداند. خروجی اعتبارسنجی‌نشده برای بازرسی، در
فیلد `outputJson` همان سطر حفظ می‌شود.

## ذخیره‌سازی و جداسازی

هر تحلیل به‌صورت یک سطر `AiAnalysis` ماندگار می‌شود: ارائه‌دهنده، مدل، وضعیت
(`PENDING` / `COMPLETED` / `FAILED`)، ‏`inputJson` (دقیقاً همان payload شواهدی که
ارسال شد — قابلیت ممیزی کامل از آنچه مدل دیده)، ‏`outputJson` (خروجی ساختاریافته
اعتبارسنجی‌شده) و `error`.

تضمین‌های جداسازی:

- لایه هوش مصنوعی **فقط** در جدول `AiAnalysis` می‌نویسد. هیچ مسیر کدی از زیرسیستم
  هوش مصنوعی به آزمایش‌ها، run ها، نتایج، لاگ‌ها یا گزارش‌ها وجود ندارد.
- گزارش‌های قطعی (`src/lib/bench/reports.ts`) خروجی هوش مصنوعی را به‌عمد کنار
  می‌گذارند — همه اعداد یک گزارش از مشاهدات خام ذخیره‌شده مشتق می‌شوند.
- آمارها توسط `stats.ts` پیش از هر دخالت احتمالی هوش مصنوعی و مستقل از آن محاسبه
  می‌شوند.

به بیان صریح: هوش مصنوعی هرگز نمی‌تواند داده‌های اندازه‌گیری‌شده را تغییر دهد — نه
مشاهدات خام، نه آمار، نه وضعیت راستی‌آزمایی و نه احکام رگرسیون. تنها جدول قابل
نوشتن برای آن، جدول تحلیل‌های خودش است.

## چرخه حیات تحلیل

endpoint مربوط به `POST /api/v1/ai/analysis` از نظر شکل asynchronous است اما درون
همان درخواست اجرا می‌شود: یک سطر `AiAnalysis` با وضعیت `PENDING` و `inputJson`
دقیق، پیش از فراخوانی ارائه‌دهنده ساخته می‌شود؛ سپس به `COMPLETED` (خروجی
اعتبارسنجی و grounding شده ذخیره می‌شود) یا `FAILED` (خطای ارائه‌دهنده، نقض schema،
رد grounding، یا run خالی — «نتیجه تکمیل‌شده‌ای برای تحلیل وجود ندارد») به‌روزرسانی
می‌شود. مسیر موفق `202 { analysisId }` برمی‌گرداند و در غیر این صورت `502` به‌همراه
پیام خطا؛ سطر ذخیره‌شده همیشه دلیل شکست را حفظ می‌کند، پس خطاها پس از وقوع هم
قابل ممیزی‌اند.

پارامترهای ارائه‌دهنده: مقدار `temperature` پیکربندی‌شده (پیش‌فرض ۰.۲ — پایین، تا
خروجی به شواهد نزدیک بماند) و یک مهلت تکمیل ۹۰ ثانیه‌ای که با promise race اعمال
می‌شود. adapter مربوط به z-ai، ‏SDK را با thinking غیرفعال صدا می‌زند؛ adapter مربوط
به Ollama درخواست `format: "json"` می‌دهد تا مدل از همان ابتدا به سمت JSON قابل
parse هدایت شود.

برای یک run می‌توان چند تحلیل اجرا کرد (مثلاً پس از تعویض ارائه‌دهنده)؛
`GET /api/v1/ai/analysis?runId=…` آنها را جدیدترین اول به‌همراه ارائه‌دهنده و مدلشان
فهرست می‌کند تا همیشه معلوم باشد کدام بک‌اند کدام تفسیر را تولید کرده است.

## انتظارات واقع‌بینانه

- تحلیل، یک کمک برای تفسیر است، نه یک علامت‌ده. بررسی grounding *کدام* واریانت‌ها
  و شناسه‌های run قابل ارجاع‌اند را مقید می‌کند، اما کیفیت متن همچنان به مدل
  بستگی دارد؛ موارد `possible_explanations` بنا به تعریف فرضیه هستند و باید در برابر
  run های جدید آزمایش شوند، نه به‌عنوان واقعیت نقل شوند.
- ترکیب `confidence: "low"` با محدودیت‌هایی درباره نتایج ناپایدار (‏CV ≥ ۱۰٪) یا
  نمونه‌های خیلی کوچک، یعنی مدل به‌درستی از ادعای مفرط خودداری کرده است. این خودش
  یک سیگنال است و باید جدی گرفته شود.
- اگر لایه هوش مصنوعی غیرفعال یا در دسترس نباشد، هیچ چیز دیگری افت نمی‌کند:
  بنچمارک، آمار، مقایسه‌ها و گزارش‌ها با آن درگیر نیستند.

## استفاده

```sh
# بررسی در دسترس بودن ارائه‌دهنده
curl -s http://localhost:3000/api/v1/ai/status

# تحلیل یک run تمام‌شده (در موفقیت کد 202؛ در شکست ارائه‌دهنده/grounding کد 502)
curl -s -X POST http://localhost:3000/api/v1/ai/analysis \
  -H "Content-Type: application/json" -d '{"runId": "clx…"}'

# خواندن تحلیل‌های ذخیره‌شده برای آن run
curl -s "http://localhost:3000/api/v1/ai/analysis?runId=clx…" | python3 -m json.tool
```

پیش‌شرط‌ها: run باید موجود و تمام‌شده باشد (`COMPLETED` یا `FAILED`؛ یک run در حال
اجرا خطای `409` می‌دهد) و حداقل یک نتیجه تکمیل‌شده داشته باشد — یک run خالی به‌جای
تولید تحلیلِ هیچ، با خطای صریح شکست می‌خورد.
