# روش‌شناسی بنچمارک

این سند دقیقاً توضیح می‌دهد که CodeBench چگونه اندازه‌گیری می‌کند — از جمله بخش‌هایی
که بی‌نقص نیستند. هدف این است که خواننده خودش تشخیص دهد تا چه حد به یک عدد اعتماد
کند.

همه زمان‌ها **میانگین زمان هر عملیات** (`avgt`، بر حسب ns/op) هستند. تعریف
«عملیات» برای هر واریانت در [ALGORITHMS_FA.md](ALGORITHMS_FA.md) آمده و در هر
سه زبان یکسان است.

## سیاست warm-up در هر هارنس

هر هارنس گرم‌سازی را به همان روشی انجام می‌دهد که برای runtime خودش اصیل — و
لازم — است:

| هارنس | مکانیزم warm-up | نگاشت فیلد `warmup` در config |
|---|---|---|
| Google Benchmark (C++) | یک **حلقه بدون زمان‌سنجی** صریح در `main()` که عملیات اندازه‌گیری‌شده را `warmup` بار روی یک workload تازه‌ساخته اجرا می‌کند، *پیش از* آنکه `benchmark::RunSpecifiedBenchmarks()` کنترل را بردارد. cache ها و branch predictor گرم می‌شوند؛ JIT‌ای برای گرم کردن وجود ندارد. | متغیر محیطی `CB_WARMUP` (پیش‌فرض ۲) |
| JMH (Java) | `-wi <warmup>` تکرار warm-up به مدت `-w 1s` برای هر کدام، که توسط JMH پیش از تکرارهای اندازه‌گیری‌شده و در یک JVM منفرد fork شده (`-f 1`) اجرا می‌شود. متد اندازه‌گیری‌شده به حالت پایدارِ کامپایل‌شده با JIT می‌رسد. | `warmup` (با کف ۱) |
| pyperf (Python) | `-w <warmup>` مقدار warm-up که توسط worker process ایزوله pyperf جمع‌آوری و دور ریخته می‌شود، پیش از مقادیر اندازه‌گیری‌شده `-n <repetitions>`. | `warmup` (با کف ۰) |

سایر تنظیمات ثابت هارنس‌ها: موتور C++ با `--benchmark_min_time=0.05s` per تکرار
اجرا می‌شود؛ تکرارهای اندازه‌گیری‌شده JMH حداقل `-r 200ms` هر کدام با
`-Xms256m -Xmx1024m` و profiler مربوط به `gc` فعال اجرا می‌شوند؛ pyperf با
`--min-time 0.05s` و یک worker process منفرد (`-p 1`) اجرا می‌شود.

## تکرارها و مشاهدات خام

- فیلد `repetitions` در config آزمایش (پیش‌فرض ۵، حداقل ۲) تعداد درخواستی تکرارهای
  اندازه‌گیری‌شده است.
- **هر تکرار به‌صورت یک observation خام** در `BenchmarkResult.observations`
  (ns/op) ذخیره می‌شود. Google Benchmark per تکرار یک `real_time` می‌دهد؛ JMH از
  `primaryMetric.rawData` per هر تکرار اندازه‌گیری‌شده یک مقدار می‌دهد؛ pyperf per
  هر مقدار جمع‌آوری‌شده یک مقدار می‌دهد (ثانیه به ns تبدیل می‌شود).
- تمام آمارها از مشاهدات خام و توسط `src/lib/bench/stats.ts` محاسبه می‌شوند —
  هرگز توسط هارنس‌ها و هرگز توسط هوش مصنوعی: `n`، `min`، `max`، `mean`،
  `median`، انحراف معیار نمونه‌ای (با مخرج n − 1)، صدک‌های `p5 / p25 / p75 /
  p95 / p99` (درون‌یابی خطی R-7، پیش‌فرض numpy/pandas)، `iqr`، `mad` (انحراف
  مطلق میانه‌ای نسبت به میانه)، `cv` (stddev / |mean|) و یک فاصله اطمینان t با
  اطمینان ۹۵٪ روی میانگین.
- `statsJson` ذخیره‌شده داده مشتق‌شده است؛ همیشه از `observations` قابل
  بازمحاسبه است.

## داده پرت (outlier)

outlier ها با قانون استاندارد IQR تشخیص داده می‌شوند: observation هایی خارج از
بازه `[Q1 − 1.5·IQR, Q3 + 1.5·IQR]` در `stats.outliersIqr` فهرست می‌شوند. این
مقادیر **علامت‌گذاری و نگه داشته می‌شوند، هرگز بی‌صدا حذف نمی‌شوند**. میانگین،
انحراف معیار و فاصله اطمینان آن‌ها را شامل می‌شوند؛ میانه و MAD در برابرشان
مقاوم‌اند. این یک انتخاب آگاهانه است: outlier اطلاعاتِ مربوط به محیط اندازه‌گیری
است (وقفه scheduler، GC، رویداد حرارتی) و حذف آن دقیقاً همان بی‌ثباتی‌ای را که
خواننده باید بداند پنهان می‌کرد.

## طبقه‌بندی پایداری

ضریب تغییرات (CV) مشاهدات یک نتیجه به این صورت طبقه‌بندی می‌شود:

| CV | پایداری | تفسیر |
|---|---|---|
| کمتر از ۳٪ | `stable` | به میانه اعتماد کنید؛ مقایسه‌ها در این سطح معنادارند |
| ۳٪ تا کمتر از ۱۰٪ | `moderate` | قابل استفاده، اما نویز run-to-run را در ذهن نگه دارید |
| ۱۰٪ و بیشتر | `unstable` | coordinator هشدار ثبت می‌کند؛ اندازه‌گیری را ناپایدار در نظر بگیرید و اجرای مجدد را بررسی کنید |

## ورودی‌های قطعی

تمام ورودی‌های بنچمارک از یک PRNG مشترک و bit-identical ساخته می‌شوند که در
TypeScript (`src/lib/bench/prng.ts`)، C++، Java و Python پیاده‌سازی شده است.

### SplitMix64

```
GOLDEN = 0x9e3779b97f4a7c15

mix(z):
    z = (z ^ (z >> 30)) * 0xbf58476d1ce4e5b9   (mod 2^64)
    z = (z ^ (z >> 27)) * 0x94d049bb133111eb   (mod 2^64)
    return z ^ (z >> 31)

constructor(seed):
    s   = (seed + GOLDEN) mod 2^64     // seed-hashing step
    state = mix(s)

next():
    state = (state + GOLDEN) mod 2^64
    return mix(state)

randInt(lo, hi):                        // inclusive bounds
    return lo + (next() mod (hi - lo + 1))
```

**مرحله seed-hashing** (جمع کردن ثابت نسبت طلایی و یک بار mix در constructor)
seed های نزدیک به هم را از هم مستقل می‌کند: seed های متوالی، جریان‌های نامرتبط
تولید می‌کنند.

**بایاس modulo:** تابع `randInt` از کاهش به پیمانه بازه استفاده می‌کند؛ پس هر
گاه 2^64 مضرب دقیق بازه نباشد، برخی مقادیر به‌اندازه‌ای خیلی جزئی محتمل‌ترند.
این بایاس *در هر زبان یکسان است* (هر چهار پیاده‌سازی از یک ترتیب عملیات استفاده
می‌کنند)، پس دیتاست‌ها بین زبان‌ها و در طول زمان bit-identical می‌مانند. بایاس
مستند شده است، نه رفع‌شده؛ برای ورودی‌های بنچمارک از نظر آماری بی‌اهمیت است.

### مولدهای دیتاست (محدوده دقیق مقادیر)

برای یک `(dataset, n, seed)` مشخص، هر زبان دقیقاً یک آرایه/رشته/گراف یکسان تولید
می‌کند:

| دیتاست | مولد | مقادیر |
|---|---|---|
| `random_int` | یک `randInt(-2147483648, 2147483647)` per عنصر | کل بازه signed 32 بیتی |
| `sorted` | شروع با `randInt(0, 1000)`، هر مقدار بعدی += `randInt(0, 100)` | نانزولی |
| `reverse_sorted` | شروع با `randInt(0, 1000)`، هر مقدار بعدی −= `randInt(0, 100)` | ناصعودی |
| `nearly_sorted` | جریان sorted، سپس `max(1, n/100)` جابه‌جایی در `i = randInt(0, n−2)` و `j = min(n−1, i + randInt(1, 50))` | یک جریان RNG پیوسته |
| `duplicate_heavy` | `randInt(-50, 50)` per عنصر | ۱۰۱ مقدار متمایز |
| `search_mixed` | آرایه `arr[i] = 2i` (n مقدار زوج متمایز)؛ n کوئری: اندیس زوج → hit یعنی `arr[randInt(0, n−1)]`، اندیس فرد → همان مقدار + ۱ (miss تضمینی) | دقیقاً ۵۰٪ hit |
| `graph_sparse` | گراف جهت‌دار، ۶ یال per گره: `to = randInt(0, n−1)`، وزن `randInt(1, 1000)` | خودحلقه ممکن است |
| `text_corpus` | الفبای A/C/G/T؛ الگوی تصادفی ۳۲ کاراکتری؛ corpus تصادفی n کاراکتری که الگو در موقعیت `⌊n/2⌋` روی آن بازنویسی شده | حداقل یک تطابق تضمینی |
| `bounded_matrix` | دو ماتریس n×n با درایه‌های `randInt(-100, 100)` | |
| (داخلی) `distinct_shuffle` | شافل Fisher–Yates روی `0..n−1` | برای workload های صف اولویت و hash map |

## راستی‌آزمایی

صحت، پیش از زمان‌سنجی و جدا از آن بررسی می‌شود:

1. **checksum.** ورودی‌ها و خروجی‌ها به شکل canonical کدگذاری می‌شوند (مثلاً
   مقادیر اعشاریِ join شده با کاما؛ `arr|queries` برای جستجو؛ `count|offsets`
   برای تطبیق رشته) و با **FNV-1a 64** هش می‌شوند (offset basis مقدار
   `0xcbf29ce484222325`، prime مقدار `0x100000001b3`، خروجی hex حروف کوچک ۱۶
   کاراکتری). FNV-1a و SplitMix64 در هر چهار کدبیس bit-identical پیاده‌سازی
   شده‌اند.
2. **کیس‌های ثابت راستی‌آزمایی.** هر موتور زبان، واریانت خود را روی ورودی‌های
   کوچک ثابت با seed ثابت `0xC0DEBEEF` اجرا می‌کند:
   - مرتب‌سازی: `n = 257` روی هر پنج دیتاست مرتب‌سازی
   - جستجو: `search_mixed` با `n = 257`
   - ساختمان داده: `random_int` با `n = 257`
   - گراف: `graph_sparse` با `n = 61` گره
   - رشته: `text_corpus` با `n = 1000`
   - ماتریس: `bounded_matrix` با `n = 9` (یعنی 9×9)
3. **reference پیاده‌سازی.** یک reference با TypeScript
   (`src/lib/bench/reference.ts`) هر واریانت را برای شفافیت — نه سرعت —
   پیاده‌سازی کرده است. پس از هر run، coordinator checksum کیس‌های ثابت را از
   reference بازمحاسبه و مقایسه می‌کند (`refMatch`). ناهمخوانی نتیجه را `FAILED`
   می‌کند — آن عدد یک اندازه‌گیری معتبر نیست.
4. **برابری بین‌زبانی.** نتایج بر اساس (variant, dataset, size) گروه‌بندی
   می‌شوند. وقتی بیش از یک زبان حضور دارد، checksum ورودی و checksum خروجی در
   گروه باید یکسان باشد؛ در غیر این صورت مقایسه نامعتبر است و همه سطرهای گروه
   failed می‌شوند. یک دروازه مستقل، `bun scripts/verify-crosslang.ts`، هر ۲۰
   واریانت را بررسی می‌کند — ۱۲۰ مقایسه checksum بین reference و سه موتور — و
   باید پیش از اعتماد به هر زمان‌سنجی پاس شود.

راستی‌آزمایی همیشه بدون زمان‌سنجی، روی همان ورودیِ دقیق اندازه‌گیری‌شده به‌علاوه
کیس‌های ثابت، و پیش از شروع اندازه‌گیری هارنس اجرا می‌شود.

## قراردادهای عملیات اندازه‌گیری‌شده

تعاریف زیر در همه زبان‌ها یکسان پیاده‌سازی شده‌اند؛ همین تعاریف هستند که اعداد
بین‌زبانی را قابل مقایسه می‌کنند.

- **مرتب‌سازی‌های مخرب، کپی defensive را شامل می‌شوند.** مرتب‌سازی ورودی‌اش را
  نابود می‌کند و هر تکرار باید داده یکسان ببیند. بنابراین کپی آرایه سالم ورودی
  *درون* عملیات اندازه‌گیری‌شده است — در C++ و Java و Python به یک اندازه.
  مقایسه‌های بین‌زبانی مرتب‌سازی این کپی O(n) و برابر را در هر دو طرف شامل
  می‌شوند.
- **پیمایش گراف، ریست آرایه visited را شامل می‌شود.** BFS/DFS (و آرایه‌های
  distance/done در Dijkstra) per عملیات تخصیص/صفر می‌شوند تا یک پیمایش کامل
  اندازه‌گیری شود، نه یک پیمایش مجددِ گرم.
- **ساخت hash-table برای lookup ها، setup بدون زمان‌سنجی است.** واریانت
  `search.hash_lookup` جدول n درایه‌ای را حین setup می‌سازد (‏`@Setup` در JMH /
  setup در GB / ‏`prepare()` در pyperf)؛ فقط خود lookup اندازه‌گیری می‌شود. در
  مقابل، `datastructures.hash_map_ops` یک چرخه کاملِ insert همه + lookup همه +
  delete همه را همراه با ساخت کانتینر اندازه‌گیری می‌کند.
- **کانتینر تازه per عملیات.** چرخه‌های ساختمان داده (آرایه پویا، صف، صف‌های
  اولویت، hash map) یک کانتینر تازه درون عملیات می‌سازند تا سیاست رشد و رفتار
  تخصیص حافظه هم بخشی از اندازه‌گیری باشند.
- **مصرف نتیجه.** هر زبان جلوی حذف کد مرده را به روش اصیل خودش می‌گیرد: یک sink
  از نوع volatile به‌همراه `DoNotOptimize`/`ClobberMemory` در C++، ‏`Blackhole`
  در JMH، و برگرداندن مقدار انباشته از closure مربوط به pyperf در Python.

## دسته‌های انصاف

واریانت‌ها با برچسب `hand-written` یا `standard-library` مشخص می‌شوند و این دو
دسته را نباید یک نوع مقایسه فرض کرد:

- `sorting.std_sort` یعنی `std::sort` (در C++) در برابر `Arrays.sort` روی
  `int[]` (در Java؛ quicksort دو محوری) در برابر `list.sort` (در CPython؛
  Timsort). اینها الگوریتم‌های متفاوتی هستند که تیم‌های متفاوتی نوشته‌اند؛
  تفاوت‌شان بهاندازه مهندسی کتابخانه به runtime مربوط است.
- `datastructures.pq_std` یعنی `std::priority_queue` با `std::greater` در برابر
  `java.util.PriorityQueue` در برابر `heapq`.
- `search.hash_lookup` و `datastructures.hash_map_ops` یعنی
  `std::unordered_map<long,long>` در برابر `HashMap<Long,Long>` در برابر `dict`.
  واریانت‌های Java کلیدهای `Long` را box می‌کنند — این هزینه اصیل این workload در
  Java است و بخشی از چیزی که اندازه‌گیری می‌شود، نه یک تصادف.
- واریانت‌های دست‌نویس (merge sort، ‏quicksort، ‏binary heap، ‏BFS/DFS/Dijkstra،
  ‏KMP و…) ساختار الگوریتمی یکسانی در هر زبان پیاده می‌کنند، پس نسبت‌های
  بین‌زبانی‌شان به مقایسه «زبان + runtime» نزدیک‌تر است.

یک جزئیات عمدی: واریانت‌های صف اولویت روی یک **جریان کلیدهای متمایزِ شافل‌شده**
کار می‌کنند (Fisher–Yates روی `0..n−1`) تا ترتیب pop قطعی و بین پیاده‌سازی‌ها
یکسان باشد — با کلیدهای تکراری، ترتیب عناصر برابر می‌توانست بین کانتینرها
متفاوت و در عین حال درست باشد، که خروجی‌ها را غیرقابل مقایسه می‌کرد.

Dijkstra درایه‌های heap را به‌صورت `dist · 2^20 + node` کدگذاری می‌کند تا شکستن
تساوی در heap (فاصله‌های برابر) در هر زبان یکسان resolve شود (فاصله‌ها تا زیر
2^41 دقیق می‌مانند).

## احکام رگرسیون

`GET /api/v1/comparisons?baseline=…&candidate=…` دو run را مقایسه می‌کند. برای هر
جفت همخوان (variant, language, size) اختلاف میانه (candidate نسبت به baseline) را
محاسبه و حکم صادر می‌کند:

- **INCONCLUSIVE** وقتی `|Δ%|` زیر آستانه معناداری عملی است (پیش‌فرض ±۱۰٪،
  قابل تنظیم در settings)، *یا* وقتی `|Δ%|` زیر تغییرات ترکیبی run-to-run — یعنی
  CV ترکیبی `sqrt(cv_baseline² + cv_candidate²)` — است. تغییری که از نویز قابل
  تشخیص نیست، رگرسیون گزارش نمی‌شود.
- **REGRESSION / IMPROVEMENT** فقط وقتی تغییر از هر دو (آستانه و نویز ترکیبی)
  بزرگ‌تر باشد.
- **NOT-COMPARABLE** وقتی راستی‌آزمایی در یکی از دو طرف شکست خورده باشد.
- **NO-DATA** وقتی آن جفت در یکی از طرف‌ها موجود نیست.

گزارش مقایسه، قابلیت مقایسه را هم بیان می‌کند: `workload-differs` وقتی هر یک از
(واریانت‌ها، زبان‌ها، datasetType، سایزها، seed) بین دو run متفاوت باشد و
`environment-differs` وقتی مدل CPU یا تعداد هسته‌ها فرق داشته باشد.

## محدودیت‌های شناخته‌شده

صریح گفته می‌شود:

- **ماشین مشترک / مجازی‌سازی‌شده.** زمان‌ها فقط منعکس‌کننده محیط ثبت‌شده‌اند. خود
  snapshot محیط یادآور می‌شود که CPU گزارش‌شده توسط سیستم‌عامل ممکن است مجازی
  باشد. اینها اعداد مرجع و جهانی عملکرد نیستند.
- **coordinator همزمان وب‌اپ را هم سرو می‌کند.** بنچمارک‌ها به‌صورت سری و در
  زیرپروسه‌ها اجرا می‌شوند، اما سرور Next.js (و هر چیز دیگری روی host) می‌تواند
  بر سر CPU رقابت کند.
- **fork منفرد JVM.** هر job جاوا در یک JVM تازه اجرا می‌شود (`-f 1`). این،
  job ها را با زبان‌های دیگر هم‌تراز می‌کند (یک پروسه، یک job) به بهای عدم
  میانگین‌گیری روی چند incarnation مربوط به JVM.
- **PYTHONHASHSEED=0.** job های Python با hash seed ثابت برای تکرارپذیری اجرا
  می‌شوند. عملیات اندازه‌گیری‌شده به ترتیب پیمایش set/dict وابسته نیست، اما این
  یک انتخاب محیطی مستند است.
- **بایاس modulo** در تولید مقیدشده (بالا توضیح داده شد) — بین زبان‌ها یکسان و
  برای ورودی بنچمارک از نظر آماری بی‌اهمیت.
- **نمونه‌های کوچک.** با ۵ تکرار پیش‌فرض، فاصله اطمینان t با ۹۵٪ پهن است
  (‏t = 2.776 با df = 4). فاصله‌های اطمینان گزارش می‌شوند؛ تفاوت‌های زیر آستانه
  را inconclusive در نظر بگیرید.
- **نتایج مختص محیط، رتبه‌بندی جهانی زبان‌ها نیستند.** نسبت ۳ برابری C++/Python
  روی این ماشین برای یک workload، به workloadها، پیاده‌سازی‌ها یا ماشین‌های دیگر
  تعمیم نمی‌یابد. گزارش‌ها این محدودیت را تکرار می‌کنند و system prompt لایه
  هوش مصنوعی ارائه نتایج به‌صورت رتبه‌بندی جهانی را ممنوع کرده است.
